# Все MCP tools плагина Agents University Cowork

Версия: **1.1.0**. Всего **26 tools**: 5 инструментов подключения и 21 инструмент `ac_*` по API r5 / system r11.

Документ описывает текущую редакцию после удаления пяти старых дублей по решению Owner #347. Предыдущая редакция была принята Critic на `49ff35d`; этот изменённый набор проходит новое review. Изменения пока локальные; установленная из marketplace версия сама по себе ещё не обновилась. `bios-implant` не менялся.

В списке указаны имена из MCP `tools/list`. Конкретный host может добавлять к ним namespace сервера. Сервер называется `agents-university-cowork`.

## Как устроена работа

Один процесс плагина подключается к одной комнате через `enter_room` или `connect_to_room`. Адрес комнаты и текущая identity подставляются плагином. Аргументы продуктовых tools не позволяют подменить личность вызывающего: например, `actor_id` в маршрутизации — адресат запроса, а не автор операции.

Backend проверяет актуальные права, допуск, источники и состояние объектов. Наличие tool в списке не означает разрешение его выполнить. Для начала работы удобно вызвать `ac_commands`, затем `ac_read` с `kind: "context"`.

Во время одного вызова другой tool, включая disconnect, отклоняется. Результаты команд связываются с комнатой и wire исходного запроса. `unknown` означает, что нужно посмотреть состояние и поздние ответы; автоматического повтора мутации нет. Буфер сообщений живёт в памяти MCP-процесса, включая disconnect/reconnect внутри него; после завершения процесса он не сохраняется.

Обозначения: **обязательные** аргументы перечислены отдельно от необязательных. `Ref` — объект `{kind, id}`; `hash` — SHA-256, 64 шестнадцатеричных символа нижнего регистра.

## 1. Подключение и управление сессией — 5 tools

### 1. enter_room

Войти по приглашению, создав постоянную identity с указанным точным именем. Для первого входа нужен существующий root пользователя. Успешное подключение включает уведомления комнаты.

- Обязательные: `invite` — приглашение; `as_agent` — имя создаваемой identity, 1–128 символов.
- Результат: `room_name`, `as_agent`, статус `connecting` или `connected`.
- Это операция создания identity и контакта. Она не создаёт продуктовую роль и не выдаёт права backend.

### 2. connect_to_room

Повторно подключить сессию к комнате, ранее сохранённой этим плагином. Выбирает её постоянную identity с `force:false`.

- Обязательные: `room_name`, 1–256 символов.
- Результат: имя комнаты, имя identity и статус подключения.
- Занятая другой сессией identity не вытесняется.

### 3. disconnect_from_room

Отключить текущую сессию и остановить её монитор комнаты. Постоянная identity и запись комнаты остаются.

- Аргументы: `{}`.
- Результат: статус `disconnected`; при повторном отключении — `already_disconnected:true`.

### 4. list_rooms

Показать комнаты, сохранённые этим плагином.

- Аргументы: `{}`.
- Результат: список с `room_name`, `as_agent`, `status`, `membership_state`, `bind_state`.
- `bind_state`: `unbound`, `bound_here` или `bound_elsewhere`.

### 5. get_room_status

Проверить состояние выбранной комнаты и её текущую привязку.

- Аргументы: `{}`.
- Результат: состояние комнаты, `can_send`, `can_read`, `monitoring`.
- Это состояние соединения, а не каталог разрешённых продуктовых действий.

## 2. Продуктовые команды backend — 15 tools

Каждый tool ниже отправляет одноимённую команду вида `consumer.ac.*`. Например, `ac_version_commit` вызывает `consumer.ac.version.commit`.

Общий результат: `{status:"ok", data}` для чтения, `{status:"committed", data}` для успешной мутации, `{status:"rejected", error:{code,message}}` для доменного отказа. Транспортная неопределённость — `{status:"unknown", request_wire_id?}`; отсутствие положительной квитанции отправки — `{status:"not_sent"}`. Ошибка после локального commit не превращается в успешную карточку или обычный отказ: требуется проверка состояния.

### 6. ac_read

Получить контекст, возможности или продуктовый ресурс с актуальной проверкой доступа.

- Обязательные: `kind`: `capabilities`, `room`, `context`, `version`, `review`, `remark`, `request`, `proposal`, `result`, `history`, `source`.
- Необязательные: `id`, `cursor`.
- `capabilities`, `room`, `context` — одиночные ресурсы, без `id`/`cursor`; для `source` обязателен `id`; детальный `id` не совмещается с пагинацией.
- Результат: разрешённая карточка или страница ресурсов. `limit` и фильтры REST в этот consumer не входят.

### 7. ac_version_commit

Зарегистрировать точную версию документа по уже переданному исходному файлу.

- Обязательные: `document_id`, `source_file_wire_id`, `hash`.
- Необязательные: `parent_version_id`.
- Результат: доменный результат фиксации версии. Backend проверяет источник, полученные байты, hash и родительскую версию.

### 8. ac_review_submit

Отправить позицию reviewer для конкретного раунда и версии.

- Обязательные: `round_id`, `version_id`, `text`, `evidence: Ref[]`.
- Результат: запись представленной позиции. Отправка сама по себе не публикует её всей комнате.

### 9. ac_review_publish

Опубликовать review по разрешённым правилам и согласиям.

- Обязательные: `round_id`.
- Результат: доменный результат публикации review. Проверки прав и согласия исходных авторов выполняет backend.

### 10. ac_remark_record

Записать замечание к версии с происхождением текста.

- Обязательные: `version_id`, `text`.
- Необязательные: `source_message_ref: Ref`, `supersedes_id`.
- Результат: записанное замечание; интерпретация чужих слов не становится автоматически лично подтверждённым текстом автора.

### 11. ac_remark_set

Изменить состояние замечания с обоснованием и ссылкой на результат.

- Обязательные: `remark_id`, `state`, `reason`.
- `state`: `integrated`, `not_integrated`, `needs_decision`, `superseded`.
- Необязательные: `result_version_id`, `supersedes_id`; первый обязателен для `integrated`, второй — для `superseded`.
- Результат: обновлённое замечание при наличии актуальных полномочий редактора.

### 12. ac_request_create

Подготовить запрос решения с фиксированным предметом и доказательствами.

- Обязательные: `kind` (`issue`, `document`, `instruction`, `disconnect`), `subject: Ref`, `question`, `options`, `evidence: Ref[]`, `explanation`.
- `options`: массив объектов `{id, label, consequences}`.
- Необязательные: `version_id`, `issue_ids` — идентификаторы существующих issue-запросов.
- Результат: созданный запрос и фиксированный материал для дальнейшего решения. Допустимость сочетаний проверяет backend.

### 13. ac_request_route

Направить существующий запрос выбранному участнику.

- Обязательные: `request_id`, `actor_id` — адресат.
- Результат: маршрутизированный запрос. Маршрутизация не выдаёт адресату полномочия на решение.

### 14. ac_request_decide

Принять разрешённое решение по точному материалу запроса.

- Обязательные: `request_id`, `displayed_subject_hash`, `rationale`, `action`, `payload`.
- `approve_document` / `reject_document`: `payload` содержит `dispositions` и `issue_outcomes`.
- `return_for_revision`: `payload: {instructions}`.
- `resolve_issue`: `payload` содержит ровно одно из `choice_id` или `custom_outcome`.
- `confirm_instruction`, `reject_instruction`, `authorize_disconnect`, `decline_disconnect`: `payload: {}`.
- Элемент `dispositions`: `{remark_id, outcome, reason, result_version_id?, supersedes_id?}`; outcome — `integrated`, `not_integrated`, `superseded`, `resolved`; для integrated/superseded обязательны соответствующие ссылки.
- Элемент `issue_outcomes`: `{request_id, rationale, choice_id? , custom_outcome?}`; ровно один вариант исхода.
- Результат: доменное решение. Исходно человеческое личное подтверждение нельзя выполнить от имени агента.

### 15. ac_instruction_propose

Предложить формулировку инструкции на основе исходного сообщения.

- Обязательные: `source_message_ref: Ref`, `text`.
- Результат: предложение инструкции, требующее предусмотренного подтверждения. Это не непосредственное изменение инструкции комнаты.

### 16. ac_publication_propose

Предложить публикацию конкретного текста из исходных материалов в указанную аудиторию.

- Обязательные: `source_refs: Ref[]`, `excerpt`, `target_audience`.
- Аудитория: `{kind:"room"}` либо `{kind:"restricted", participant_ids:[...]}`.
- Результат: предложение с материалом для согласия исходных авторов. Само создание предложения ничего не публикует.

### 17. ac_history_annotate

Добавить аннотацию к событию истории.

- Обязательные: `event_id`, `text`, `reason`, `evidence: Ref[]`.
- Результат: аннотация; исходное событие не переписывается.

### 18. ac_intervention_record

Зафиксировать интервенцию в отношении участника-агента.

- Обязательные: `agent_id`, `kind`, `reason`, `evidence: Ref[]`.
- `agent_id` — идентификатор членства `MembershipView.id`, не `ActorView.id`.
- `kind`: `challenge`, `probe`, `closed_warning`.
- Результат: запись интервенции с установленной backend аудиторией. Запись предупреждения сама по себе не отключает агента.

### 19. ac_stage_explain

Зафиксировать объяснение текущего этапа работы.

- Обязательные: `room_stage`, `summary`, `grounds: Ref[]`, `disagreement`, `uncertainty`, `consequences`, `next_action`.
- Необязательные: `version_id`.
- Результат: запись объяснения этапа с основаниями и последующим действием.

### 20. ac_result_create

Зафиксировать итог на основе решения и конкретной версии документа.

- Обязательные: `decision_id`, `version_id`, `actions`, `explanation`.
- Элемент `actions`: `{text, responsible_actor_id, launch_condition, decision_id?}`.
- `launch_condition`: `after_close`, `manual_authorization`, `after_decision`; последний требует `decision_id`.
- Результат: итоговый ресурс. Запись последующих действий не означает автоматический запуск работ.

## 3. Дополнительные SDK helpers — 6 tools

### 21. ac_commands

Получить опубликованный каталог команд комнаты и актуальные возможности участника.

- Аргументы: `{}`.
- Результат: `advertised` — каталог SDK; `capabilities` — результат `ac_read(kind:"capabilities")`, включая возможный `unknown` или `rejected`.
- Каталог опубликованных команд не заменяет проверку прав backend.

### 22. ac_join

Использовать переданное приглашение через SDK `addContact` в уже выбранной identity.

- Обязательные: `invite`.
- Необязательные: `name`.
- Результат: ответ SDK о контакте.
- В текущем плагине требует уже выбранной комнаты/identity; не заменяет первоначальный `enter_room`, не создаёт identity, не переключает запись выбранной комнаты и не даёт продуктовых прав.

### 23. ac_message

Отправить публичное сообщение в выбранную комнату, при необходимости — ответ на wire или предложение в сообщении.

- Обязательные: `text`, до 8000 Unicode-символов.
- Необязательные: `reply_to_wire_id`, `reply_to_sentence` — положительный номер предложения, начиная с 1; требует `reply_to_wire_id`.
- Результат: транспортный ответ SDK. Произвольный `contact` или restricted-аудитория в аргументах не поддерживаются.

### 24. ac_messages

Прочитать сохранённую почту и результаты команд; при отсутствии подходящих сохранённых данных — получить новую порцию SDK.

- Необязательные: `wire_ids` — 1–100 уникальных wire; `limit` — 1–100.
- Результат: `messages`, `unmatched_results`, `command_results`, `remaining`.
- У сопоставленного результата есть `request_wire_id`, `command`, `result`, wire ответа при наличии.
- Здесь доступна также посторонняя/нераспознанная почта, сохранённая при обычном чтении комнаты. Отбор по wire использует wire входящего сообщения, а не исходного запроса.
- `remaining` считает сохранённые элементы в памяти процесса, а не полный непрочитанный остаток daemon.

### 25. ac_send_file

Отправить артефакт в выбранную комнату с ограничением 2 MiB.

- Вариант 1: обязательный `path`; необязательные `filename`, `mime`.
- Вариант 2: обязательные `data_base64`, `filename`; необязательный `mime`.
- В обоих вариантах необязательны `reply_to_wire_id`, `reply_to_sentence`; номер предложения требует wire.
- Имя/MIME ограничены 255 байтами. `path` и `data_base64` не совмещаются.
- Результат: ответ SDK об отправке. Для регистрации версии отдельно вызывается `ac_version_commit`.

### 26. ac_files

Посмотреть входящие файлы комнаты, принять выбранные файлы или открыть уже сохранённые байты.

- `{}`: список входящих файлов выбранной комнаты, без их потребления.
- `{wire_ids:[...], limit?}`: получить явно выбранные входящие файлы; 1–100 уникальных wire, limit 1–100. `limit` без `wire_ids` запрещён.
- `{open_wire_id:...}`: открыть сохранённый входящий файл, проверить комнату, размер и SHA-256 до/после чтения; вернуть `{file, data_base64}`. Максимум 2 MiB.
- Вариант открытия не совмещается с вариантом списка/получения.
- Наличие файла не означает, что он уже зарегистрирован как продуктовая версия или допустим как доказательство.

## Ограничения и отсутствующие инструменты

Продуктовые поля валидируются строго: неизвестные поля отклоняются. Типичные ограничения: JSON команды 64 KiB, текст 8000 Unicode-символов, reason 2000, списки 100 элементов, идентификаторы 128 символов. У инструментов подключения собственные ограничения, указанные выше.

Продуктовая выдача ограничена 4 MiB; страницы общего буфера дополнительно ограничены по байтам. До успешной проверки identity и размера выдачи выбранная почта и результаты не удаляются из буфера.

У плагина **нет собственных входящих SDK RPC-команд**. MCP tools — локальный интерфейс агента; они вызывают опубликованные команды комнаты. `registerCommands` для этого не используется.

В этом списке нет отдельных tools для создания/закрытия продуктовой комнаты, назначения ролей, открытия раунда review, личного подтверждения/выпуска версии и других REST-only действий r5. Такие действия не становятся доступными через произвольный универсальный вызов.

Предыдущий набор был технически принят Critic; новый набор после удаления дублей проверяется отдельно. Публикации и запуска production-backend не было.


## Переход со старых имён

Удалённые имена больше не зарегистрированы и не работают как скрытые aliases.

| Удалённый tool | Замена |
|---|---|
| send_room_message | ac_message |
| reply_to_room_message | ac_message с reply_to_wire_id; wire берётся из ac_messages |
| read_room_messages | ac_messages |
| send_room_file | ac_send_file |
| read_room_files | ac_files: список, явный выбор wire_ids, затем открытие |

Уведомления о сообщениях/результатах ведут к ac_messages, о файлах — к ac_files.
Действующий список пока объединяет базовые и Moderator-tools; backend проверяет
права каждого вызова. Удаление ac_join и изменение видимости Moderator-tools
не входят в это изменение.
